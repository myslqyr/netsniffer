# 03 测试与提交清单

## 1. 测试原则

- 使用自己控制的机器和服务生成演示流量。
- 对同一份 PCAP，对照 Wireshark 的实际字段验证解析结果。
- 核心自动化测试覆盖协议边界和 TCP 重组；GUI 的常规布局和按钮操作使用人工验收即可。
- 测试数据使用合成或脱敏内容，不提交包含凭据和个人通信的抓包。

## 2. 准备可重复的演示流量

### IPv4 / ICMP

```bash
ping -4 -c 4 127.0.0.1
```

需要捕获 loopback 并支持其实际链路类型。如果初版仅支持 Ethernet，改为测试可达的局域网主机并选择对应网卡。

### IPv6 / ICMPv6

```bash
ping -6 -c 4 ::1
```

同样注意 loopback 链路类型。外部 IPv6 不可用时，可用本地样例 PCAP 验证 IPv6 解析。

### 明文 HTTP / TCP

在仅含演示文件的目录中启动服务：

```bash
python3 -m http.server 8000 --bind 127.0.0.1
```

在另一个终端请求：

```bash
curl --http1.1 http://127.0.0.1:8000/
```

捕获 loopback；检查请求方法、路径、响应状态以及 TCP 握手。端口 8000 也用于证明 HTTP 识别不只依赖 80 端口。该场景是否出现跨 TCP 段取决于实际运行，不能用一次请求代替固定的跨段测试样例。

### DNS / UDP（可选扩展）

如果系统有 `dig`，向明确指定的可达 DNS 服务器发送查询，并捕获对应网卡。DNS 可能使用缓存、本地 stub、TCP 或加密传输，因此普通浏览网页不保证产生预期的 UDP/53 流量。

## 3. 功能验收矩阵

| 项目 | 操作 | 预期 |
| --- | --- | --- |
| 网卡 | 刷新并切换网卡 | 名称和地址正确，无有效网卡时有提示 |
| 权限 | 无抓包权限启动捕获 | 提示原因，界面仍可操作 |
| 启停 | 连续启停至少 10 次 | 无崩溃、重复后台线程和明显资源泄漏 |
| 空闲停止 | 无流量时停止 | 在设计的退出时限内完成，窗口不冻结 |
| 基础解析 | 导入各协议样例 | 地址、端口、长度、标志与对照一致 |
| 捕获过滤 | `tcp`、`udp port 53`、非法表达式 | 合法条件生效，非法条件报错 |
| 显示过滤 | 切换协议并清空条件 | 正确显示和恢复缓存中的记录 |
| 三窗格 | 点击不同包和字段 | 详情、字节内容和高亮对应同一包 |
| 排序 | 排序后选择记录 | 不因行号变化展示错误数据 |
| PCAP | 导出后再次导入 | 包数、字节、长度和时间符合声明 |
| HTTP | 端口 8000 的请求 | 可按内容识别 HTTP |
| 非 HTTP | 80 端口的任意其他字节 | 不仅凭端口认定 HTTP |
| TCP 归组 | 双向传输和后续新连接 | 方向正确，新旧连接分开 |
| 资源上限 | 持续流量达到缓存上限 | 按策略淘汰且有计数，仍可操作 |
| 文件错误 | 损坏 PCAP、不可写路径 | 报错明确，不崩溃 |

## 4. 必须准备的边界样例

解析器测试：

- Ethernet/IP/TCP 头分别被截断。
- IPv4 IHL、总长度以及 TCP data offset 不合法。
- TCP options、空载荷 ACK、UDP 最短合法报文。
- VLAN、IPv6 扩展头、IPv4/IPv6 非首片。
- 未支持的链路类型和未知协议号。
- 原始长度大于捕获长度。

TCP 重组测试：

- 顺序到达、乱序到达、完全重复和部分重叠。
- 内容冲突的重叠片段、永久缺口、抓包从连接中途开始。
- SYN/FIN 序列占位、序列号回绕、RST 结束。
- 同一五元组先后建立多个连接。
- HTTP 请求行或头部跨多个 TCP 段。
- 同一 TCP 载荷中包含多条 HTTP 消息。
- 超出重组资源预算，得到明确的不完整状态。

每个样例保存预期字段、重组字节或缺口位置，不只检查“程序没有崩溃”。

## 5. 性能记录

在报告中写清测试机器、网卡、流量来源、持续时间与过滤条件，记录：

- 捕获包数和每秒包数。
- CPU 与内存使用情况。
- libpcap 提供的接收/丢包统计及其平台口径。
- 应用队列丢弃、缓存淘汰、重组淘汰分别是多少。
- GUI 是否能保持交互。

不把“缓存淘汰”写成“网卡丢包”，也不从一次低流量演示推导出高速抓包能力。
