# 02 分步开发指南

每一阶段完成后保留一个可以演示的版本，并提交一次有意义的 Git 记录。以下命令是给开发者执行的步骤，本次编写文档没有安装依赖或运行抓包。

## 阶段 1：建立环境与最小窗口

目标：先验证编译工具、Qt 和 libpcap 可用。

1. 在 Debian/Ubuntu 环境准备依赖：

   ```bash
   sudo apt update
   sudo apt install build-essential cmake pkg-config qt6-base-dev libpcap-dev
   ```

2. 创建 `src/main.cpp` 和根目录 `CMakeLists.txt`。
3. CMake 设置 C++17、`CMAKE_AUTOMOC ON`，使用 `find_package(Qt6 REQUIRED COMPONENTS Widgets)`；通过 `PkgConfig` 和 `pkg_check_modules(PCAP REQUIRED IMPORTED_TARGET libpcap)` 链接 `Qt6::Widgets`、`PkgConfig::PCAP`。
4. `main.cpp` 创建 `QApplication` 和 `QMainWindow`，先显示空窗口。
5. 构建、运行：

   ```bash
   cmake -S . -B build
   cmake --build build -j
   ./build/netsniffer
   ```

6. 配置 `.gitignore`，忽略 `build/`、临时抓包文件和本地编辑器文件。保留专门审查过的测试样例。

产物：可重复构建的工程、一个能打开和关闭的窗口。

验收：删除或换一个构建目录后仍能重新构建，不依赖手工设置的绝对库路径。

## 阶段 2：实现命令行抓包内核

目标：不接 GUI，先证明能收到真实网络包。

1. 用 `pcap_findalldevs()` 枚举网卡，复制名称、描述、地址，随后释放枚举链表。
2. 创建 `CaptureConfig`，包含网卡名、snaplen、混杂模式、读取超时、捕获过滤条件。
3. 使用 `pcap_create()` 创建句柄，设置参数，再调用 `pcap_activate()`；分别处理警告和错误。
4. 调用 `pcap_datalink()` 保存链路类型。初期选明确支持的 Ethernet 网卡，不直接选 `any`。
5. 通过 `pcap_next_ex()` 或合适的循环接收数据，区分收到包、超时、错误、离线 EOF。
6. 每次收到包，按 `caplen` 复制原始字节，保存时间戳、`caplen` 和 `len`。
7. 暂时打印时间、捕获长度、原始长度，不急着解析所有协议。
8. 用 RAII 包装 `pcap_t`；实现明确的结束和错误清理路径。
9. 设计停止机制。Linux 可结合可选择的捕获描述符和唤醒描述符等待；注意并非每个捕获源都提供可用描述符。不要把 packet-buffer timeout 当成所有环境都保证的停止时限。

产物：`capture/`、`RawPacket`、命令行诊断入口。

验收：有流量时能抓到包；无流量时仍能主动结束；退出后能重新开始抓包；权限不足时显示可理解的错误。

权限安排：抓包需要相应权限。开发阶段可用单独的命令行抓包程序验证；产品形态优先考虑最小权限的抓包辅助进程。不要把以 root 身份运行整个 GUI 当作默认部署方案。

## 阶段 3：编写基础协议解析器

目标：从字节解析出地址、端口、协议和摘要。

1. 编写只读字节读取器，提供 `readU8`、`readBE16`、`readBE32` 和安全切片。每次读取前检查剩余长度。
2. 解析 Ethernet 的源/目的 MAC 与 EtherType；处理 VLAN 标签后继续解析下一层。
3. IPv4：读取版本、IHL、总长度、协议号、地址、TTL 和分片字段。验证 `IHL >= 20`、总长度不小于头部长度；解析范围受 IP 总长度和实际捕获长度共同限制。
4. IPv6：读取固定头，按 next-header 遍历支持的扩展头，限制遍历次数；遇到分片时避免将非首片误解析成 TCP/UDP。
5. TCP：解析端口、序列号、确认号、data offset、flags、窗口；校验头部长度后确定载荷范围。
6. UDP：解析端口和长度；普通报文长度应不小于 8 字节，不能越过 IP 有效载荷。IPv6 jumbogram 等暂不支持情况明确降级。
7. ICMP/ICMPv6：解析 type、code，以及已支持消息的标识符等字段。
8. 补充 ARP：按头部声明的地址长度检查，提取常见 Ethernet/IPv4 ARP 请求和应答。
9. 产生 `ParsedPacket`，未知协议保留原始数据并显示编号。

产物：不依赖 GUI 的 `parser/` 与小规模确定性测试样例。

验收：地址、端口、TCP flags 等与同一 PCAP 在 Wireshark 中的结果一致；截断头、非法长度、未知协议均不会越界或崩溃。

注意：不要直接把任意包地址强转成 C++ struct。未对齐访问、结构体填充、网络字节序都可能导致错误。

## 阶段 4：接入图形界面

目标：实现课件展示的三窗格浏览器。

1. 顶部加入网卡下拉框、刷新、开始、停止、清空按钮。
2. 使用 `QTableView + QAbstractTableModel` 显示序号、时间、源、目的、协议、长度、摘要。
3. 使用分隔布局加入详情树和只读 Hex/ASCII 区域。
4. 选中列表记录后，通过包 ID 获取数据，生成字段树和原始字节展示；点击字段可高亮对应字节。
5. 把抓包放入工作线程，通过有界队列交换数据。GUI 可每 50–100 ms 批量取数据；该数值为初始调优值。
6. 设置初始资源预算，例如最多保留 1 万个包且原始字节不超过 64 MiB，任一上限到达即淘汰旧记录。实际进程内存还包含解析树等开销，必须另外测量。
7. 对已淘汰记录和当前选中记录做一致性处理，不能留下悬空引用。
8. 状态栏显示抓包状态、包数、缓存淘汰数、应用丢弃数，以及可用的 libpcap 丢包统计。
9. 实现状态机：空闲 → 启动中 → 捕获中 → 停止中 → 空闲；异常回到可重试状态。

产物：可以操作的抓包主窗口。

验收：抓包期间可以拖动和缩放窗口；连续开始/停止不崩溃；关闭窗口能结束工作线程；缓存达到上限后继续运行。

## 阶段 5：实现捕获过滤和显示过滤

目标：完成课程要求的协议筛选能力。

1. 捕获过滤输入框接受 BPF 表达式，例如 `tcp`、`udp port 53`、`host 192.168.1.10`。
2. 在抓包线程内调用 `pcap_compile()` 和 `pcap_setfilter()`；使用合适的网掩码或 `PCAP_NETMASK_UNKNOWN`，随后释放编译产物。
3. 错误表达式显示具体错误信息。初版只允许停止后修改捕获过滤，减少并发修改句柄的复杂度。
4. 显示过滤提供 HTTP、TCP、UDP、IPv4、IPv6、ICMP 协议选择，以及 IP、端口输入。
5. 对 `ParsedPacket` 的协议集合匹配：HTTP 包也应匹配 TCP，IPv6 TCP 包也应匹配 IPv6。
6. 通过代理模型或可见包 ID 索引过滤，清空显示条件后恢复缓存中的所有记录。
7. 区分“捕获包数”和“当前显示包数”。

产物：两类过滤控件与匹配逻辑。

验收：非法 BPF 不导致崩溃；显示过滤不删除底层记录；HTTP 类型由后续应用层识别模块补齐，不能把 `port 80` 直接作为 HTTP 判据。

## 阶段 6：实现 PCAP 保存与离线读取

目标：可以复现抓包结果，为后续应用层和重组开发提供固定输入。

1. 通过 `pcap_dump_open()`/`pcap_dump()` 写入原始记录，保留捕获长度、原始长度和时间戳。
2. 明确保存范围：初版导出“当前缓存中的全部包”；如果要保存完整会话，另做持续写盘功能，不能声称缓存导出包含已淘汰数据。
3. 用 `pcap_open_offline()` 读取文件，复用同一解析器，并采用与实时捕获相同的批量更新方式。
4. 校验链路类型，处理文件截断、不可读路径和写盘失败。
5. 一份传统 PCAP 文件对应一种链路类型。不同会话或不同链路类型不直接混写；混合接口记录作为后续 PCAPNG 扩展。
6. 保留文件时间精度，或者进行明确且正确的转换。

产物：打开 PCAP、保存 PCAP 的菜单和模块。

验收：导出的文件可由 Wireshark 打开；重新导入后包数、原始字节、长度和时间一致（若做精度转换，按声明的精度比较）。

## 阶段 7：实现 HTTP 与可选 DNS 分析

目标：体现“协议分析”，而不只是一张包列表。

1. 第一版识别单个 TCP 载荷中完整的 HTTP/1.x 请求行或状态行，验证基本语法，不能只查找任意位置的 `GET` 字符串。
2. 提取 method、request target、HTTP version、status code 和 Host 等已捕获字段。
3. 头部不完整时显示“待重组/数据不足”，不把半包直接判成非法 HTTP。
4. 为后续 TCP 重组预留接口，让应用层解析器接收连续字节流，而不是只能接收单个包。
5. 完成重组后，补充按 `Content-Length`、chunked 等规则确定 HTTP 消息边界，支持同一连接上的连续消息；对不支持的 framing 明确标记。
6. HTTPS 初版展示 TLS 或“疑似 TLS”，根据实际解析能力决定标签，不显示虚构的明文 URL。
7. 可选 DNS：从 UDP DNS 开始，解析 transaction ID、查询名、类型和回答；压缩指针需要边界检查、循环检测及跳转次数上限。

产物：HTTP 详情和摘要、可选 DNS 详情。

验收：非 80 端口上的明文 HTTP 也能识别；80 端口上的任意非 HTTP 数据不被自动标为 HTTP；跨段识别能力在下一阶段完成并验证。

## 阶段 8：实现 TCP 流追踪和重组

目标：先实现连接归组，再恢复双向字节流。

1. 用协议、地址族、源/目的 IP 和端口形成双向规范化连接键，记录每个包的方向。
2. 展示每条连接的首末时间、双向包数、字节数及连接状态。
3. 处理五元组复用：新 SYN、连接关闭、超时等因素共同决定是否创建新的连接实例。
4. 每个方向维护预期序列号和乱序片段缓存，按 TCP 序列号空间进行比较，考虑 32 位回绕；SYN/FIN 各占一个序列号。
5. 对连续载荷追加输出，乱序载荷先缓存，重传部分去重；对重叠且内容不同的数据采用明确策略，例如保留先到数据并记录冲突。
6. 抓包从连接中途开始时，以实际首见序列建立相对位置，标记“中途开始”。缺失字节显示缺口，不能直接拼成一段看似完整的数据。
7. 给每条连接及全局缓存设置字节上限、超时和淘汰策略；超过限制时显示重组不完整。
8. GUI 加入“追踪 TCP 流”，分别显示两个方向的文本/Hex；跨方向显示只表示观察顺序，不声称恢复唯一的应用交互顺序。
9. 把连续字节交给 HTTP 解析器，更新流级协议和相关包的关联信息。

产物：连接列表、TCP 流窗口、重组测试样例。

验收：同一双向连接归为一流；乱序可以恢复；重复报文不重复输出；缺包有标记；相同端口的新连接不会混入旧流。

## 阶段 9：有余力再做的功能

1. 进程关联：在 Linux 中获取连接与 socket 信息，再关联到进程；记录查询时刻，处理权限限制、短连接消失、网络命名空间等情况。显示“未知”是合法结果，不根据端口猜 PID。
2. 统计：协议分布、每秒字节数和活跃连接。说明统计基于全部捕获还是当前显示结果，以及字节数采用哪种长度。
3. 时序图：从实际 TCP 标志和方向生成 SYN/SYN-ACK/ACK、FIN、RST 等事件。
4. 性能：先测量队列、解析和 GUI 刷新的开销，再决定是否优化线程、缓冲区或采用更高级的捕获技术。
